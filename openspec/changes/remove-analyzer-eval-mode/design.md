## Goals / Non-Goals

**Goals:**

- analyzer의 동작을 절차 **하나**로 만든다. 모드 판별이 사라진다.
- 사용자 후보 처리를 방안 생성 절 안의 **짧은 규칙 하나**로 흡수한다.
- `orchestra/SKILL.md`의 안전장치를 **유지한 채** 호출 형태만 평소 호출로 되돌린다.
- 편집을 최소 범위 부분 수정으로 한정해 파일 손상 위험을 없앤다.

**Non-Goals:**

- `README.md` 수정. 확인 결과 평가 모드를 언급하지 않는다. **읽기만 하고 손대지 않는다.**
- `docs/verification-2026-09-08.md` 수정. 날짜가 박힌 **과거 기록**이다.
  당시 상태를 그대로 보존하는 것이 이 문서의 존재 이유다.
- `designer.md` / `worker.md` / `reviewer.md` / `regression-verifier.md` / `finalizer.md` /
  `preparer.md` 수정. 이번 요청과 무관하다.
- 3단계 "★ 사용자가 안을 고른다" 관문 자체의 변경. 그대로 둔다.
- analyzer.md를 목표 줄 수까지 줄이는 것. 아래 D5 참조.

## Decisions

### D1. 대상 파일은 전부 `Edit`로 부분 수정한다. `Write`로 전체 재작성 금지

이번 세션에 리치 마크다운 편집기가 개입해 `[[ORCA_RICH_MD:...]]` 토큰이 삽입되고,
굵게 표시가 백틱 안으로 밀리고, 들여쓰기가 붕괴한 사고가 실제로 있었다(정리 모드로 복구).
전체 재작성은 같은 결과를 낸다.

- 대안: `sed -i`로 일괄 치환 → 여러 줄 블록 삭제·삽입에서 앵커를 잡기 어렵고,
  실패해도 조용히 지나간다. 채택하지 않는다.
- 대안: `Write`로 다시 쓰기 → 위 사고 재현. 채택하지 않는다.

### D2. 사용자 후보 규칙은 `### 3. 방안 최소 3가지 만들기` 안에 넣는다

넣을 위치: `- **코드가 아예 없는 프로젝트면 축이 다르다.**` 로 시작하는 항목 **다음**,
`- 각 안마다 반드시:` **앞**.

- 앞의 축(axis) 목록은 "어떤 안을 만들지"를 정하는 부분이고, 사용자 후보도 "안 목록에
  무엇이 들어가는가"의 문제라 같은 자리다.
- `- 각 안마다 반드시:` 뒤에 넣으면 그 항목의 하위 목록으로 읽힐 위험이 있다.

넣을 문장 (이 네 줄 그대로):

```
- **프롬프트에 사용자가 낸 후보가 함께 오면, 그것도 안 하나로 넣어 같은 형식으로 평가한다.**
  기존 안을 지우지 말고 번호를 이어 붙인다.
  **성립하지 않으면 분명히 말해라.** 무엇이 막는지 파일:줄로 짚는다.
  사용자 아이디어라고 봐주는 건 도움이 아니라 손해다.
```

버린 `## 사용자 안 평가` 절 6단계 중 살린 것과 버린 것:

| 원래 항목 | 처리 |
|---|---|
| 1. 기존 3안과 똑같은 형식으로 평가 | **살림** — 위 첫 줄 |
| 2. 실제 코드로 성립하는지 확인 | **버림** — `### 2. 코드베이스 분석` 전체가 이미 이걸 시킨다 |
| 3. 성립 안 하면 파일:줄로 짚어 분명히 | **살림** — 위 셋째·넷째 줄 |
| 4. 부분 성립이면 다듬은 변형안 제시 | **버림** — "진짜로 다른 길을 3가지"가 이미 변형안을 허용한다 |
| 5. analysis.md에 다음 번호로 추가, 기존 안 유지 | **살림** — 위 둘째 줄 |
| 6. 기존 추천과 비교해 의견 다시 | **버림** — `### 4. 내 의견 내기`가 이미 시킨다 |

### D3. `feasible=` 필드는 없앤다. 대체 필드를 만들지 않는다

각 안마다 이미 **"요구사항 충족"** 항목이 있고(`### 3`의 마지막 불릿, 보고 형식의
`### N안` 줄), 성립 여부는 거기에 적힌다. `RESULT` 줄에 같은 정보를 한 번 더 두는 것은
중복이고, 조건부 필드라 파싱하는 쪽(오케스트레이터)에도 분기를 만든다.

- 대안: `feasible=`을 무조건 필수 필드로 승격 → 사용자 후보가 없을 때 의미가 없다.
  채택하지 않는다.

### D4. orchestra의 안전장치 절은 **지우지 않고 호출 형태만** 바꾼다

`### 사용자가 목록에 없는 자기 안을 냈을 때` 절은 그대로 두고, 그 안에서:

- `analyzer를 **평가 모드로 다시 부른다:**` → `analyzer를 **다시 부르되, 그 안을 추가 후보로 얹어 보낸다:**`
- 프롬프트의 `평가할 안: <...>` → **평소 analyzer 호출과 같은 구성** + `사용자가 낸 안: <...>` 한 줄 추가
- **`바로 designer로 가지 마라. **검증 안 된 안을 설계하면 worker가 벽에 부딪힌다.**` 는 그대로 둔다.**
- 절 끝의 두 불릿(다시 고르게 한다 / 성립 안 하면 근거를 그대로 전한다)도 그대로 둔다.

바꿀 프롬프트는 2단계 analyzer 호출(`## 2. analyzer 호출`)의 구성을 그대로 따른다.
그래야 "특별한 모드가 아니라 평소 하던 일"이라는 채택안의 취지가 문서 형태로도 드러난다.

파이프라인 그림 화살표:

```
   ↓    사용자가 자기 안을 내면 → analyzer 재호출(평가 모드) → 다시 고르게 한다
```
→
```
   ↓    사용자가 자기 안을 내면 → 그 안을 후보로 얹어 analyzer 재호출 → 다시 고르게 한다
```

### D5. 군살 빼기는 열거된 항목으로 한정한다

analyzer.md를 문장 단위로 훑은 결과, **모드 분기 두 절을 빼고 나면 남는 제거 대상은
형식 결함 하나뿐**이다. 이 파일은 이미 밀도가 높다.

**제거/수정할 것 (이것뿐):**

- `S1` — 블록인용(`> 읽어서 따르는 것이 기본이다...`) **뒤에** 떨어져 나와 있는
  들여쓴 괄호 문장 `  (specs 델타가 어떤 형태여야 하는지 알면 실현 가능한 방안을 낼 수 있다)`.
  원래 `- 기준을 정확히 알아야 할 때는 ... Read로 읽어라.` 항목에 붙어야 할 부연인데
  블록인용 때문에 떨어져 나가 **뜬 문장**이 됐다. 지우지 말고 그 항목 바로 아래로 **옮긴다.**
  (지우면 "왜 읽어야 하는지"가 사라진다. 옮기면 형식 결함만 없어진다.)

**검토했지만 남기기로 한 것** (reviewer가 "왜 안 뺐지"를 대조할 수 있게 남긴다):

| 문장 | 남기는 이유 |
|---|---|
| `고르는 건 사용자가 한다. 너는 고를 수 있게 만들어 준다.` (17줄) | 「하지 말아야 할 것」의 같은 취지 항목과 겹쳐 보이지만, 이쪽은 **역할 규정**이고 저쪽은 **금지 목록**이다. 도입부에서 역할을 못 박지 않으면 안을 하나로 좁혀 오는 회귀가 난다 |
| `설계 문서도, 코드도 쓰지 않는다. 네가 쓰는 파일은 analysis.md 하나뿐이다.` (18줄) | 「하지 말아야 할 것」은 **금지 목록(블랙리스트)**, 이 문장은 **허용 목록(화이트리스트)**이다. 화이트리스트가 더 강하고, 둘 중 하나만으로는 구멍이 남는다 |
| `Bash로도 바꾸지 마라 (sed -i, 포매터 --write 금지)` (19줄) | analyzer는 Bash를 쓴다. 이 문장이 없으면 실제로 파일을 고칠 수 있다 |
| `단 explore는 결론을 내주지 않는다...` (32–33줄) | 없으면 explore만 돌리고 방안 없이 끝내는 회귀가 난다 |
| `Skill 도구가 없을 수 있다` 블록인용 (38–41줄) | 없으면 "스킬을 못 부른다"며 멈춘다. 실측으로 확인된 실패 모드다 |
| store 처리 절 (50–55줄) | 없으면 store 환경에서 명령이 엉뚱한 곳을 본다 |
| `resolvedOutputPath를 파일로 취급하지 마라` (67줄) | 글롭 경로를 파일로 열려다 실패하는 것을 막는다 |
| 정량 요구사항 기준선 측정 (83–85줄) | 없으면 숫자 없는 "빨라질 것이다"가 나온다. reviewer가 대조할 값이 사라진다 |
| 방안 축(axis) 목록 (89–93줄) | 「진짜로 다른 길 3가지」를 실제로 만들게 하는 유일한 발판이다 |
| analysis.md 맨 위 경고 줄 (112–115줄) | 없으면 reviewer가 추천안을 기준으로 삼아 정상 작업을 반려한다 |

- 대안: 「하지 말아야 할 것」 절을 통째로 지우고 도입부에 합치기 → 지침을 한 곳에서
  확인할 체크리스트가 사라진다. 다른 에이전트 파일과 구조도 어긋난다. 채택하지 않는다.
- 대안: 보고 형식의 `### 1안 / 2안 / 3안` 예시를 하나로 줄이기 → "최소 3가지"라는
  요구가 형식에서 눈에 안 보이게 된다. 채택하지 않는다.

## Risks / Trade-offs

- **[리치 마크다운 편집기가 다시 파일을 손상시킨다]** → D1(Edit 부분 수정만).
  작업 마지막에 `grep -c 'ORCA_RICH_MD'` = 0, 코드펜스 개수 = 기준선 일치,
  frontmatter 5줄 온전을 **명시적으로 확인**한다.
- **[군살을 빼다 규칙을 지운다 = 회귀]** → D5에서 제거 대상을 `S1` 하나로 못 박고,
  남기기로 한 문장을 표로 남겼다. 목록 밖 문장을 지우면 안 된다.
- **[안전장치가 말만 남고 실제로 안 도는 형태가 된다]** → orchestra의 새 호출 예시가
  2단계 호출과 같은 구성인지 눈으로 대조한다. `사용자가 낸 안:` 이라는 키가 프롬프트에
  들어 있고, analyzer.md의 새 규칙이 "프롬프트에 사용자가 낸 후보가 함께 오면"으로
  받게 되어 있어야 **양쪽이 맞물린다.** 한쪽만 고치면 조용히 끊긴다.
- **[줄 번호로 위치를 잡다 어긋난다]** → 편집이 진행되면 아래쪽 줄 번호가 밀린다.
  worker는 앵커 문자열로 찾고, 위에서 아래 순서(description → 두 가지 모드 → S1 →
  방안 절 → 사용자 안 평가 절 → RESULT)가 아니라 **아래에서 위 순서로 고치거나**
  매번 `grep -n`으로 다시 확인한다.
- **[트레이드오프] `feasible=` 제거로 오케스트레이터가 한눈에 성립 여부를 못 본다** →
  대신 보고서 본문의 각 안 "요구사항 충족" 줄과 "내 추천"을 읽어야 한다.
  한 줄 요약이 사라지는 대가로 조건부 필드 분기가 없어진다. 채택안대로 간다.

## Migration Plan

문서 수정뿐이라 배포·마이그레이션이 없다. 되돌리기는 `git checkout -- <파일>`이다.
단 `docs/example-run.md`는 `.git/info/exclude`로 git 추적 제외라 **git으로 되돌릴 수 없다.**
그 파일을 고치기 전에 사본을 남긴다(작업 4.1).
