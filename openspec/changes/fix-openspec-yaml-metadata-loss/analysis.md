# 분석: fix-openspec-yaml-metadata-loss

> 이 문서의 추천은 analyzer 의견이다. 사용자가 최종 선택한 안은 decision.md에 있다.

작성: 2026-09-08 / OpenSpec 1.12.0 / 대상 파일 `.claude/agents/preparer.md`, `.claude/agents/designer.md`

---

## 1. 지금 상태 (관찰한 사실)

### 문제의 두 지침

- `.claude/agents/preparer.md:146`
  `` `<changeRoot>/.openspec.yaml`에 `skip_specs: true` 한 줄을 추가하고, 보고서에 그 사실과 이유를 적는다. ``
- `.claude/agents/designer.md:158`
  `` `<changeRoot>/.openspec.yaml`에 `retire_capabilities: true`를 추가하고 보고서에 그 사실과 이유를 적는다. ``

둘 다 **"추가하라"고만 한다.** 파일이 이미 있다는 사실도, 어떤 도구로 어떻게 추가하라는 것도 없다.
두 에이전트 모두 `tools:` 에 `Bash, Write, Edit` 를 다 갖고 있다 (preparer.md:5, designer.md:5).
그래서 셋 중 아무거나 고를 수 있고, 그중 두 가지가 파일을 깨뜨린다.

### `openspec new change` 가 만들어 두는 내용 (실측)

```
schema: spec-driven
created: 2026-09-08
```
`--goal "..."` 을 주면 `goal:` 키가 하나 더 붙는다 (실측). 즉 보존해야 할 키는 `schema:` 하나가 아니다.

### 실패 모드 매트릭스 (scratchpad에 별도 openspec 프로젝트를 만들어 전부 직접 재현)

| # | 에이전트가 할 법한 행동 | 파일 결과 | `validate` | `validate --strict` | `status --json` | 눈에 띄는가 |
|---|---|---|---|---|---|---|
| A | `printf 'skip_specs: true\n' > .openspec.yaml` (덮어쓰기) | `schema:` 유실 | **1** | 1 | 1 | 에러 문구가 원인을 정확히 말해 줌 |
| B | `>>` 로 두 번 실행 (재시도·되돌아옴) | `skip_specs:` 키 중복 | **1** | 1 | 1 | `the file is not valid YAML` — 원인 문구가 A와 **다름** |
| C | 마지막 줄에 개행이 없는 파일에 `>>` | `created: 2026-09-08skip_specs: true` | **1** | 1 | 1 | **원인 문구 없음.** "델타가 없다"만 나옴 |
| D | `retire_capabilities` 를 덮어쓰기로 설정 | `schema:` 유실 | **0** | **0** | **1** | **validate 는 통과한다** |
| E | 가드 붙인 append (아래 관용구) | 정상 | 0 | 0 | 0 | — |

이 표에서 나오는 것 세 가지가 proposal 이 아직 모르는 사실이다.

1. **C 가 제일 위험하다.** 마커가 조용히 무시되고, 남는 에러는
   `Change must have at least one delta` 뿐이다. 그런데 `preparer.md:154` 는
   *"아직 델타가 없어서 실패할 수 있다(exit=1). 그건 정상이다"* 라고 적어 놨다.
   즉 **문서가 이 실패를 "정상"이라고 가르치고 있다.** (`preparer.md:155` 가 절반은 막아 주지만,
   154 와 155 가 같은 exit=1 을 서로 반대로 해석한다.)
2. **B 는 재시도에서 터진다.** worker→designer 되돌아오기, `openspec-update-change` 경로 등
   같은 지침이 두 번 실행되는 길이 파이프라인에 실제로 있다. 단순 append 지침은 멱등하지 않다.
3. **D 는 designer 의 검증을 그냥 통과한다.** `designer.md:187~199` 는 `validate --strict` 의
   **종료코드로 판정하라**고 못 박았는데, retire 경로에서는 그게 0 이다.
   같은 절에 있는 `openspec status --change "<이름>"` 은 exit=1 로 실패하지만,
   designer.md 어디에도 **status 의 종료코드를 보라는 말이 없다.**
   → 깨진 메타데이터가 designer 를 통과해서 finalizer 까지 간다.

### CLI 로 확인할 수 있는 것 / 없는 것 (실측)

- `skip_specs` 는 **읽어 볼 수 있다**: `openspec status --change X --json` 의
  `artifacts[] 중 specs.status == "skipped"`. 마커가 안 먹으면 `ready` 로 남는다.
- `retire_capabilities` 는 **status/show/list JSON 어디에도 안 나온다.** 읽어 볼 수단이 없다.
- 다만 **두 경우 모두** `openspec status --change X --json` 의 **종료코드**가
  메타데이터 파손을 잡아낸다 (깨지면 `Error: Invalid metadata: ... schema ...` 로 exit=1).
  → **범용 게이트는 `validate` 가 아니라 `status` 다.**

### CLI 에 마커용 플래그는 없다 (실측)

`openspec new change --help` 옵션: `--description / --goal / --schema / --json / --store` 뿐.
`openspec change` 하위 명령은 `show / list / validate` 뿐. 즉 **손으로 쓰는 것 말고 길이 없다.**
(CLI 수정은 이번 범위 밖이다.)

### 실측으로 확인한 안전한 관용구

```bash
f="<changeRoot>/.openspec.yaml"
grep -q '^skip_specs:' "$f" || printf '\nskip_specs: true\n' >> "$f"
```
- 앞의 `\n` 이 개행 없는 마지막 줄을 닫아 준다 → 실패 모드 C 차단 (실측 exit=0)
- `grep -q` 가드가 중복 키를 막는다 → 실패 모드 B 차단 (3번 돌려도 한 줄, 실측 exit=0)
- `>>` 라서 기존 키를 하나도 안 지운다 → 실패 모드 A/D 차단
- 파일이 이미 개행으로 끝나면 빈 줄이 하나 생기는데 YAML 에서 무해하다 (실측 exit=0, specs=`skipped`)

### 문서들이 서로 참조하는 구조 (중복 관리 관점)

- `.openspec.yaml` 마커를 언급하는 곳: `preparer.md:143,146,155,176`, `designer.md:135,158`,
  `finalizer.md:83,104,128`, `README.md:182`, `orchestra/SKILL.md:368`.
  **쓰는 곳은 preparer / designer 둘뿐이고**, 나머지는 "있으면 이렇게 동작한다"는 읽는 쪽 설명이다.
- 에이전트가 다른 문서를 **경로로 Read 해서 따르는 선례는 이미 있다**
  (`preparer.md:25`, `designer.md:29,40` → `.claude/skills/openspec-*/SKILL.md`).
- 배포 경로 (`install.sh:74-77`): `.claude/agents/*.md` **글롭** + `.claude/skills/orchestra` **디렉터리 통째** + `settings.json`.
  → `.claude/agents/` 밑 하위 디렉터리는 **복사되지 않는다.**
  → `.claude/agents/*.md` 에 새 파일을 두면 복사는 되지만 Claude Code 가 그걸 **에이전트 정의로 읽는다.**
  → 공용 문서를 새로 만든다면 `.claude/skills/orchestra/` 안이 유일하게 안전한 자리다.
- `.claude/settings.json` allow 목록에 `Bash(openspec:*)` 와 git 명령만 있다.
  `printf ... >> ...` 는 **allow 에 없다 → 권한 프롬프트가 뜰 수 있다.** (Edit/Write 도구도 마찬가지로 확인을 받는다)

## 2. 내 추측 / 확인 못 한 것

- 실제 사고가 Bash `>` 로 났는지 Write 도구로 났는지는 확정 못 했다. 다만 현재 하니스의 Write 도구는
  *"읽지 않은 기존 파일 덮어쓰기는 실패한다"* 고 되어 있어서, **Bash 리다이렉트가 더 그럴듯한 경로**다.
  → 지침이 "Write 하지 마라"만 적으면 진짜 구멍(`>`)을 못 막을 수 있다. **둘 다 막아야 한다.**
- 권한 프롬프트가 서브에이전트 실행을 실제로 얼마나 멈추는지는 이 세션에서 재현하지 않았다.
- `retire_capabilities` 를 쓰는 change 를 이 저장소가 아직 한 번도 돌린 적이 없다 (archive 디렉터리 비어 있음).
  즉 실패 모드 D 는 **아직 안 터진 지뢰**다.

## 3. 기준선 측정값

정량(성능·용량) 요구사항이 아니다 → **해당 없음.**
대신 위 실패 모드 매트릭스가 기준선이다. 고친 뒤 A~E 를 그대로 다시 돌려 A~D 가 막히는지 확인하면 된다.

## 4. 기존 spec과 부딪히는 곳

메인 spec 이 0개다 (`openspec/specs/` 비어 있음) → **spec 충돌 없음.**

다만 **proposal 의 받아들일 조건 하나가 실측과 어긋난다:**

> "두 문서의 '확인' 절에 `schema: Invalid input` 에러가 나오면 원인이 `schema:` 줄 유실임을
> 알려주는 진단 힌트가 들어간다."

이 문구 하나만 힌트로 넣으면 **실패 모드 B(다른 문구) 와 C(문구 자체가 안 나옴) 를 놓친다.**
D 는 validate 가 아예 통과하므로 힌트가 뜰 자리도 없다.
→ designer 가 6단계(“proposal 과 고른 안이 어긋나면 proposal 을 고친다”)에서 이 조건을
**"세 가지 실패 모드를 모두 짚는 진단 절차"** 로 일반화해야 한다.

## 5. 방안

### 1안: 복붙 가능한 명령 한 줄을 두 문서에 박는다 (+ status 게이트)

**무엇:** preparer.md 146행과 designer.md 158행을, 실측으로 검증한 가드형 append 관용구
코드블록으로 바꾼다. 함께 `Write 도구와 셸 '>' 리다이렉트 금지`를 명시한다.
두 문서의 "확인" 절에는 **`openspec status --change ... --json` 종료코드 게이트**와
일반화된 진단 절차(파일을 `cat` 해서 ①`schema:` 생존 ②키 중복 없음 ③마지막 줄 붙음 없음 확인)를 넣는다.
preparer.md:154 의 "exit=1 은 정상" 문구에 "단 마커를 넣었으면 정상이 아니다" 를 붙인다.

**건드릴 파일:** `.claude/agents/preparer.md` (146 부근, 150~156 확인 절, 154행),
`.claude/agents/designer.md` (158 부근, 187~200 확인 절)

**장점:**
- 해석 여지가 0 이다. 에이전트가 그대로 복사해 실행하면 실패 모드 A/B/C/D 가 **전부** 막힌다 (실측).
- 파일 2개만 바뀐다. proposal 의 "영향 파일" 과 정확히 일치. install.sh·배포 영향 없음.
- 이 저장소 철학과 맞는다: 상태 판정을 산문이 아니라 **CLI 종료코드**로 한다.

**단점 / 위험:**
- 같은 4~6줄이 두 파일에 중복된다. 나중에 갈라질 수 있다 (README:182 표까지 치면 3곳).
- `printf` 가 settings.json allow 에 없어서 권한 프롬프트가 뜰 수 있다.
- 셸 관용구를 못 박으면 도구가 없는 환경(Bash 미제공 에이전트)에 이식이 안 된다.
  단 preparer/designer 둘 다 Bash 를 갖고 있어서 지금은 문제 없다.

**드는 힘:** 작음 — 두 파일에서 각 2군데, 총 20~30줄 안팎. 검증도 scratchpad 재현으로 끝난다.

**요구사항 충족:** 전부 충족. 게다가 proposal 이 몰랐던 B/C/D 까지 막는다.
단 proposal 의 진단 힌트 조건을 일반화하는 수정이 함께 필요하다.

### 2안: 명령이 아니라 "원칙"을 적는다 (도구 무관 서술형)

**무엇:** 명령을 못 박지 않고 절차를 못 박는다.
"`.openspec.yaml` 은 `openspec new change` 가 이미 만들어 둔 파일이다.
① 먼저 Read 로 현재 내용을 읽는다 ② 마커가 이미 있으면 아무것도 하지 않는다
③ 없으면 **기존 줄을 하나도 지우지 말고** Edit 으로 마지막에 한 줄만 더한다
④ 다시 읽어 기존 키가 전부 살아 있는지 확인한다 ⑤ CLI 로 확인한다.
`Write` 도구와 셸 `>` 는 이 파일에 **금지**다."

**건드릴 파일:** 1안과 동일한 두 파일·같은 위치.

**장점:**
- 도구·플랫폼에 안 묶인다. `--goal` 처럼 **앞으로 늘어날 키에도 자동으로 맞다** ("전부 보존" 원칙).
- Edit 기반이라 개행 함정(C)이 원천적으로 안 생기고 권한 프롬프트 성격도 다른 편집과 같다.
- 저장소의 다른 지침들과 문체가 같다 (이 저장소는 원칙 서술형으로 쓰여 있다).

**단점 / 위험:**
- **산문은 해석된다.** 이 change 자체가 "산문 지침을 글자대로 따르다 사고 난" 사례다.
  같은 계열의 대응이라 재발 확률이 1안보다 높다.
- 에이전트가 ③을 Bash 로 해석하면 개행·중복 함정(B/C)이 그대로 돌아온다.
- Edit 의 `old_string` 은 파일 내용을 읽어야 정해진다(`created:` 날짜가 매번 다르고,
  `--goal` 이 있으면 마지막 줄이 또 달라진다). 절차가 실제로는 2~3스텝이라 안 짧다.

**드는 힘:** 작음 — 1안과 비슷하거나 조금 적다.

**요구사항 충족:** A/D 는 확실히 막는다. B/C 는 **원칙만으로는 보장 안 된다** —
⑤의 CLI 확인 게이트가 사후에 잡아 줄 뿐이다.

### 3안: 공통 절차를 한 파일로 빼고 두 에이전트가 Read 로 참조

**무엇:** `.claude/skills/orchestra/openspec-yaml-marker.md` (이름은 예시)를 새로 만들어
"마커를 넣는 절차 + 확인 게이트 + 진단표"를 한 번만 쓴다.
preparer.md / designer.md 에는 *"마커를 넣기 전에 이 파일을 Read 하고 그대로 따른다"* 한 줄만 남긴다.

**건드릴 파일:** `.claude/skills/orchestra/openspec-yaml-marker.md` (신규),
`.claude/agents/preparer.md`, `.claude/agents/designer.md`, (선택) `README.md:182`

**장점:**
- 중복이 0 이다. 세 번째 마커가 생기거나 절차가 길어져도 한 곳만 고친다.
- 배포가 자동으로 된다 — `install.sh:76` 이 `.claude/skills/orchestra` 를 **디렉터리째** 복사한다 (실측).
- "다른 문서를 경로로 Read 해서 따른다"는 **이미 있는 패턴**이다 (preparer.md:25, designer.md:29,40).

**단점 / 위험:**
- **읽기 한 홉이 늘어난다.** 이 저장소는 이미 "스킬을 못 불러서 안 따랐다"로 한 번 데였고
  (그래서 세 에이전트 파일에 똑같은 '읽어서 따르는 것이 기본이다' 경고가 붙어 있다),
  같은 실패를 한 번 더 만들 자리를 만드는 셈이다. 마커는 change 당 한 번 쓰는 드문 경로라 더 잘 잊는다.
- `orchestra` 스킬은 **오케스트레이터용** 문서다. 서브에이전트 전용 자료를 여기 두는 건 자리로 어색하다.
  그렇다고 `.claude/agents/` 밑에는 못 둔다 — 하위 디렉터리는 install.sh 글롭이 안 집고,
  최상위 `*.md` 로 두면 Claude Code 가 **에이전트 정의로 착각한다** (실측: install.sh:74).
- proposal 의 "영향 파일: 두 개" 를 넘어선다 → proposal 을 먼저 고쳐야 한다.
- 새 파일은 install.sh 의 `copy_if_absent` 특성상 **기존 설치본에는 안 깔린다**
  (orchestra 디렉터리가 이미 있으면 통째로 건너뛴다). 업그레이드 경로에 구멍이 생긴다.

**드는 힘:** 보통 — 새 파일 + 두 에이전트 수정 + proposal 수정 + 배포/업그레이드 경로 확인.

**요구사항 충족:** 내용상 전부 충족 가능. 다만 "에이전트가 그 파일을 실제로 읽는가"에 결과가 걸린다.

### 4안: 쓰는 방법은 그대로 두고, 확인 게이트만 강제한다 (가장 작은 수정)

**무엇:** 146행 / 158행 문구는 거의 그대로 두고 ("기존 내용을 지우지 마라" 한 문장만 추가),
대신 두 문서의 "확인" 절에 **빠져나갈 수 없는 게이트**를 넣는다.

```bash
cat "<changeRoot>/.openspec.yaml"                       # 눈으로 기존 키 생존 확인
openspec status --change "<이름>" --json >/dev/null; echo "metadata ok=$?"   # 0이 아니면 파손
```
`metadata ok` 가 0 이 아니거나 `schema:` 줄이 안 보이면 **스스로 복구한 뒤 다시 확인하고, 보고서에 적는다.**

**건드릴 파일:** `.claude/agents/preparer.md` (146행 한 문장 + 150~156 확인 절),
`.claude/agents/designer.md` (158행 한 문장 + 187~200 확인 절)

**장점:**
- 가장 적게 고친다. 원인이 무엇이든(덮어쓰기·중복 키·개행 없음·미래의 새 실수) **결과를 잡는다.**
  특히 실패 모드 D(validate 가 통과해 버리는 retire 경로)를 유일하게 정면으로 막는 게 이 게이트다.
- "상태는 CLI에서 얻는다, 짐작하지 마라" 라는 저장소 철학에 가장 곧게 붙는다.

**단점 / 위험:**
- **예방이 아니라 사후 검출**이다. 매번 한 번 깨뜨렸다가 고치는 왕복이 생긴다.
- 복구를 에이전트에게 맡긴다 → 복구 과정에서 또 덮어쓸 수 있다 (재귀적 위험).
- 실패 모드 C 는 게이트에 걸리긴 하지만(`status` 는 통과하고 `validate` 만 exit=1),
  게이트 문구를 `status` 만으로 짜면 **C 를 놓친다.** `cat` 육안 확인이 반드시 같이 있어야 한다.

**드는 힘:** 아주 작음 — 두 파일에서 각 1군데씩, 10줄 안팎.

**요구사항 충족:** 부분. proposal 의 받아들일 조건 중
"기존 내용을 보존하며 한 줄을 추가하는 **구체적 방법**이 들어간다" 를 만족하지 못한다.

## 6. 내 추천: **1안** (명령 못 박기 + status 게이트)

**이유:**

1. **이 change 자체가 "산문 지침은 해석된다"의 증거다.** 원인이 지침의 모호함인데
   대응까지 산문(2안)이면 같은 실패를 반복할 자리를 남긴다. 복붙 가능한 명령은 해석 여지가 0 이다.
2. **실측으로 A/B/C/D 를 전부 막는 관용구를 이미 확보했다.** 가드 append 한 줄이
   덮어쓰기·중복 키·개행 함정을 동시에 없앤다. 다른 안은 이 중 일부만 막는다.
3. **범위가 proposal 과 정확히 일치한다.** 파일 2개, 새 파일 없음, install.sh 무관, 배포 경로 무관.
   3안은 여기서 새 파일과 업그레이드 구멍을 끌고 들어온다.
4. **4안의 게이트를 1안이 흡수한다.** 예방(명령)과 검출(status 종료코드)을 같이 넣으면
   4안 단독의 약점(왕복·복구 중 재파손)이 사라진다. 4안을 버리는 게 아니라 1안 안에 포함시킨다.
5. 중복(1안의 유일한 단점)은 **두 곳뿐이고, 쓰는 주체도 두 에이전트뿐이다.**
   이 저장소는 이미 store 처리 문단을 7개 에이전트에 중복해 두고 잘 굴러가고 있다.
   중복을 없애려고 읽기 한 홉을 늘리는 거래는 지금 규모에선 손해다.

**우선순위:** (해석 여지 제거) > (실측으로 검증된 커버리지) > (중복 제거)

**이 판단이 뒤집히는 조건:**

- **세 번째 마커나 더 긴 공통 절차가 곧 생길 예정이라면 → 3안.** 중복 지점이 3곳을 넘으면 손익이 뒤집힌다.
- **`printf ... >>` 권한 프롬프트가 실제로 서브에이전트를 멈추게 한다면 → 2안**(Edit 기반).
  이 경우 settings.json allow 에 넣는 것도 방법이지만 그건 이번 범위 밖이다.
- **"지침 문서에 셸 명령을 박는 건 이 저장소 문체가 아니다" 라고 판단한다면 → 2안 + 4안 게이트 결합.**
  이게 차선이다. 커버리지는 1안보다 낮지만(C/B 를 예방이 아니라 검출로만 막는다) 문체는 일관된다.
